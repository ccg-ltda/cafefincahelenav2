# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Café Finca Helena: Spanish-language (es_CO) coffee storefront + admin panel. Laravel 12 (PHP ^8.2) backend, React 19 + React Router 8 + Vite 7 + Tailwind 4 frontend. UI copy, docs, and README are in Spanish.

## Commands

```sh
php artisan serve          # backend, http://127.0.0.1:8000
npm run dev                # Vite dev server (use npm.cmd in PowerShell)
npm run build              # production assets
composer dev               # server + queue + pail logs + vite via concurrently
composer test              # config:clear + php artisan test
php artisan test --filter=NameOfTest   # single test (tests/Feature, tests/Unit)
./vendor/bin/pint          # PHP formatting
php artisan admin:create   # interactive-only: create admin user
```

- Do NOT run `composer setup` or migrations without user authorization: README says DB setup is pending/not yet authorized. `.env.example` defaults to sqlite, but the local `.env` uses MySQL (`cafe_finca_helena`); back it up with `/c/xampp/mysql/bin/mysqldump.exe` (into gitignored `storage/app/private/backups/`) before migrating. All migrations have run locally (the slug one, `2026_11_18_000001_create_product_slug_redirects_table`, renamed 3 product slugs to the short ones). Still never run migrations implicitly: back up first and use `migrate --path=` for a single file.
- Tests use in-memory sqlite (`phpunit.xml`). Only placeholder `ExampleTest`s exist; no JS test/lint tooling.

## Architecture

**Single Blade shell, client-side routing.** `resources/views/app.blade.php` is the only view. Laravel returns it for `/`, admin pages, and a catch-all `Route::fallback` (excludes `api/*`). React Router (`resources/js/app.jsx`) then renders. `app.jsx` hand-matches admin paths by `pathname` and renders `<AdminPage />` outside `StorefrontProvider`; every other path goes through `StorefrontLayout` routes. The pages React renders are listed ONCE in `routes/spa.json` (admin pages and login with their titles; storefront pages with `page`, `layout` shop|origin|blog|article, title and description; the blog `articles`). Laravel reads it through `App\Support\SpaRoutes` (registers the admin `Route::view`s, gives each page its `<title>`/description, and the catch-all answers a REAL 404 for any path that is not listed or an unknown article), and `resources/js/routes.js` reads the same file (router in `app.jsx`, layout choice in `StorefrontLayout`, client-side titles). A new page = one entry there (+ its component in `app.jsx` `PAGES`); `RoutesTest` guards the list, and the article slugs must match `modules/content/articles.js`. Never decide the layout from `pathname === '/'`: `.demo-home` styles depend on the layout class.

**SEO on product pages.** `ProductPageController` serves `/producto/{slug}` with real HTTP status (200/301/404) and injects `$seo` (title, canonical, Open Graph, JSON-LD) into the Blade head; React still renders the body. Legacy SKU URLs (`/producto/fh-001`) 301 to the slug URL; `product_slug_redirects` table tracks slug changes. `SitemapController` serves `/sitemap.xml`. Admin pages get `noindex` in the layout.

**Two JSON surfaces:**
- Public API (`routes/api.php`): `GET /api/categories`, `/api/products`, `/api/products/{slug}`, `POST /api/orders` (throttled 10/min). Shaped by `app/Http/Resources/*Resource.php`.
- Admin JSON lives in `routes/web.php` under `/admin/...` (session auth, not `/api`), guarded by `EnsureStaff` (401 JSON / redirect to `/admin/login` if unauthenticated or deactivated) and then `can:<permission>` per route (403); see "Users and roles". Unknown `/admin/*` paths 404. Route order matters: literal routes like `/admin/orders/data` and `/admin/products/categories` precede `{param}` routes; id params use `whereNumber`.

**Domain.** Models: `Product` → many `ProductVariant` (SKU, price, images stored per variant), `Category`, `Order` → `OrderItem`, `Payment`, `User` (`is_admin`). Product "simple vs multi-variant" is only a UI decision based on variant count, not a data-model type. Admin product editor saves product then variant as two non-atomic requests (see `docs/admin-catalog.md`). Public catalog uses a `visible()` scope plus `is_published` on variants.

**Frontend layout** (`resources/js/`): `modules/{admin,catalog,content,storefront}` feature folders (JSX + co-located CSS), `context/StorefrontContext.jsx` (cart/store state), `layouts/StorefrontLayout.jsx`. `modules/catalog/demoProducts.js` and `modules/content/*` hold static/demo content alongside the API-backed catalog.

## Checkout / orders

- `OrderPricingService` (`app/Services`) is the only place prices, availability, shipping and totals are computed. `POST /api/orders/quote` (summary) and `POST /api/orders` (store) both use it. Shipping is 0 and `shipping_pending: true` (storefront shows "a coordinar"); add the real rule in `OrderPricingService::shipping()`, no frontend change needed.
- Validation: `QuoteOrderRequest` (cart lines) and `StoreOrderRequest extends` it (customer, delivery, consent, phone = 10 digits starting with 3). Frontend mirror: `resources/js/modules/storefront/checkoutForm.js` (also `DEPARTMENTS`). Change both together.
- `CheckoutModal.jsx`: 4 steps; progress + idempotency key persist in `localStorage` (`cfh-checkout`), key regenerates when the cart content changes; storage cleared on success. Step 3 blocks confirming until changed prices / unavailable products are reviewed; `expected_total_cop` makes the backend refuse a total that differs from the reviewed one.
- **TODO (legal): the terms and personal-data policy texts (`setPolicy('terminos' | 'privacidad')`, reference content) must be written and approved before production (Ley 1581 de 2012).** `orders.terms_accepted_at` / `data_consent_at` record the acceptance.

## Inventory

- `product_variants.stock_quantity` changes ONLY through `InventoryService` (row lock, never negative, every change writes an `inventory_movements` row: signed `quantity`, `stock_after`, automatic `reason`, optional `user_id` / `order_id`). Low-stock threshold is `low_stock_threshold` (DB default 5, not editable in the UI).
- Admin sets the exact stock: `InventoryService::setStock(variant, quantity, expectedStock, reason, user)` records the difference as an `ajuste`; `expectedStock` is the stock the form/modal opened with, and if the DB differs it throws `StockConflictException` (HTTP 409, nothing saved). Used by the stock modal (`POST /admin/products/{p}/variants/{v}/stock`, reason "Ajuste desde listado") and by the variant editor (`stock_quantity` + `expected_stock`, reason "Edición de producto"). Creating a variant takes an optional initial stock ("Stock inicial"). Movements: `GET .../stock-movements` (last 10, with `from`, `origin` Admin/Venta/Devolución).
- Checkout: `OrderController::store` calls `InventoryService::sellOrder()` inside the order transaction (locks the variants in id order, 422 naming the product and how many are left, otherwise one `venta` movement per line, reason "Venta CFH-…", `order_id`). Idempotent replays return before touching stock. `InventoryService::returnOrder($order)` puts back what that order sold (once; not wired to any admin action yet).
- Public API (`/api/products`) returns `in_stock` and `available_quantity` per variant; sold-out variants stay listed and the storefront disables them. `/api/orders/quote` lines carry `available_quantity` and `insufficient`. The storefront reconciles the stored cart with the stock on load (`reconcileCart` in `StorefrontContext`).
- Product stock state counts published variants only: `low` = one with 0 < stock <= threshold, `out` = all at 0. New or migrated variants start at 0 (= "Agotado") until the admin loads stock.
- `SKU` generation (`nextSku`) uses MySQL `REGEXP`; tests that create variants through the API must register it on SQLite (see `AdminInventoryTest`).

## Promotions

- `PromotionService` owns every promotion rule: status (current / scheduled / expired / inactive), price (`priceFor`: percentage or fixed, rounded to the nearest 100 COP, must stay between 1 and base - 1), validation (`validateForSave`: published product and variants, percentage 1-90, per-variant price check, end after start, no overlap of active promotions on a variant), and `currentForVariants()` (the promotions that apply now: active, inside dates, product and variant published; lowest price wins). `OrderPricingService`, the public API (`attachPricing`) and the product-page SEO use it; the storefront never computes a promotional price (only the admin drawer preview mirrors the formula).
- Tables: `promotions` (one product, `discount_type` percentage|fixed_amount, `discount_value`, `starts_at`/`ends_at` in UTC, `is_active`), `promotion_variant`, and `order_items.original_unit_price_cop` + `promotion_id` (RESTRICT: a promotion used in an order cannot be deleted, `DELETE` answers 409, deactivate it instead). Admin enters dates as Colombian time (`America/Bogota`, `datetime-local`); `parseLocal()` / `formatLocal()` convert.
- Public API: variants carry final `price_cop`, and only while a promotion applies `original_price_cop`, `discount_label`, `promotion_ends_at`. `/api/products` and `/api/categories` add `meta.has_promotions`: the storefront shows the virtual "Promociones" tab only when it is true. `/promociones` (`PromotionsPageController`) serves the catalogue with that tab selected, answers 200 always and is `noindex` when there is no current promotion; `sitemap.xml` lists it only while `hasCurrent()`.
- Checkout: `quote` lines add `original_unit_price_cop`; `quote.savings_cop` is "Ahorras $X" (display only, `orders.discount_cop` stays 0 for future coupons). A promotion that ends between quote and store changes the total, so the existing `expected_total_cop` check refuses the order as a price change.
- Admin: `/admin/promotions` (`AdminPromotions.jsx`, `AdminPromotionDrawer.jsx`), data under `/admin/promotions/data|products|{id}`; list rows carry a `note` (product / category / variants inactive) when a current or scheduled promotion cannot show in the store.

## Coupons

- `CouponService` owns every coupon rule: code format (`[A-Z0-9-]{3,30}`, stored uppercase, case-insensitive on entry), status (inactive > expired > scheduled > exhausted > current), `evaluate()` (validity, total uses, eligible subtotal, minimum, discount), `discountFor()` (percentage capped by `max_discount_cop`, or fixed; rounded to 100 COP, never above the eligible subtotal), `redeem()` / `releaseForOrder()` and `validateForSave()`. The discount applies to products only, never shipping; `exclude_promoted_items` drops promoted lines from the eligible subtotal.
- Tables: `coupons`, `coupon_redemptions` (one row per order, `order_id` unique; uses = rows with `released_at` null, so releasing keeps the history), `orders.coupon_id` (RESTRICT) + `coupon_code`. A coupon with redemptions/orders cannot be deleted (409), only deactivated. `releaseForOrder()` is ready but no admin action cancels orders yet.
- `OrderPricingService::price($items, $code, $email, $lockCoupon)` returns `coupon` and `discount_cop`. `quote` never fails on a bad coupon: it answers 200 without it plus `coupon_error {message, reason}`; `store` re-evaluates inside the transaction with `lockForUpdate` on the coupon and answers 422 `errors.coupon_code` (`CouponException`). Unknown/inactive/expired/scheduled all answer the same generic message ("Cupón no válido o vencido"); the other reasons are concrete.
- Rate limits are named limiters in `AppServiceProvider`: `order-quote` (30/min), `order-store` (10/min) and `coupons` (10/min per IP, only for requests carrying `coupon_code`). Never use unnamed `throttle:N,1` on these routes: they share ONE counter per IP, so ten quotes blocked the order with a 429.
- Checkout (`CheckoutModal.jsx`): the applied code lives in `cfh-checkout` (localStorage) and the quote on step 3 revalidates it. Admin: `/admin/coupons` (`AdminCoupons.jsx`, `AdminCouponDrawer.jsx`), data under `/admin/coupons/data|{id}|{id}/status`; orders list/detail show `coupon_code`.
- `npm run screenshots` also photographs the admin coupons page with `SCREENSHOT_ADMIN_EMAIL` / `SCREENSHOT_ADMIN_PASSWORD` (local server only) and the coupon checkout with `SCREENSHOT_COUPON` / `SCREENSHOT_PLACE_ORDER=1` (creates an order: throwaway database only).

## Customers

- `customers` is keyed by normalized email (`CustomerService::normalizeEmail`: trim + lowercase). `OrderController::store` calls `CustomerService::syncFromOrder()` inside the order transaction: creates the customer or refreshes name, phone, city, department and last address with the newest order's data, and sets `orders.customer_id`. A replayed idempotency key returns before this, so nothing duplicates.
- Order counts, spending and first/last purchase are NEVER stored: `CustomerListing` computes them from `orders` on every query, over `Order::valid()` (not cancelled and, when `config('shop.require_payment_before_fulfillment')` / `SHOP_REQUIRE_PAYMENT` is true, `payment_status = 'paid'`). A customer is listed only with at least one valid order. Pill counters are global (they ignore search and the active pill).
- Marketing consent (Ley 1581): the optional, never pre-ticked checkout box sends `marketing_opt_in`; it is stored on the order and sets `customers.marketing_opt_in_at`. An unticked box never erases a consent. The admin "no quiere promociones" sets `marketing_opt_out_at` (with confirmation, no undo); `Customer::acceptsMarketing()` is true only while `opt_in_at` is newer than `opt_out_at`, so only a new purchase with the box ticked re-activates it.
- Admin: `/admin/customers` and `/admin/customers/{id}` (the id opens the drawer), data under `/admin/customers/data|export|{id}/detail|{id}/marketing-opt-out`, all behind `EnsureStaff` + `can:`. The CSV export (`;`, UTF-8 BOM, formula-injection guard) logs who exported. `php artisan customers:backfill [--dry-run]` creates customers from existing orders (idempotent, oldest order first so the newest data wins).

## WhatsApp

- **`SHOP_WHATSAPP_NUMBER` is REQUIRED in production** (country code + number, digits only, e.g. `573027880823`; it is empty in `.env.example`). It lives in `config('shop.whatsapp_number')`; `app.blade.php` publishes it in `<meta name="shop-whatsapp">` and `resources/js/modules/storefront/shop.js` (`shopWhatsapp()`, `whatsappLink()`) is the only place the frontend reads it. The menu, the footers, the FAQ and the product page never hold the number by hand; with no valid number those links are hidden (the menu shows its "not configured" message).
- Storefront menu: `WhatsAppMenu` in `layouts/StorefrontLayout.jsx` (title "¿En qué te ayudamos?", 3 topics `wholesale | order_support | buying_help`). Each option opens `wa.me/{number}?text=encodeURIComponent(...)` in a new tab and calls `trackWhatsappClick()` (`POST /api/whatsapp/clicks`, 20/min per IP, `fetch` with `keepalive`, errors swallowed: tracking never blocks WhatsApp). Messages stay single-line; "Soporte" uses the reference saved in `localStorage` key `cfh-last-order` (written by `CheckoutModal` when an order is registered, valid 7 days) or "CFH-…".
- Data: `whatsapp_requests` (status new | in_progress | resolved, `assigned_to`, `internal_notes`, `resolution_note`, `customer_id` linked by phone, `order_reference`), `whatsapp_menu_clicks` (topic + page path + time ONLY: never add IP, user agent or identifiers; the server strips `?query` and `#fragment` from the path) and `whatsapp_quick_replies` (3 rows seeded inside the migration, editable from the admin, no create/delete). All tables are utf8mb4, so emojis are stored intact.
- `WhatsAppService` owns the rules: phone normalization (`App\Support\Phone`, the same one checkout uses), order reference (typed or extracted with `/CFH-[A-Z0-9]{12}/i` from the text; the admin only links the order when it exists, otherwise shows it with "(no encontrado)"), take / assign (admins only) / resolve / reopen, and the summary (30-day clicks by topic). Admin: `/admin/whatsapp` and `/admin/whatsapp/{id}` (drawer), data under `/admin/whatsapp/data|requests|quick-replies`, all behind `EnsureStaff` + `can:whatsapp.manage`.

## Activity (Historial)

- `activity_logs` is the immutable audit trail of administrator actions (`/admin/activity`, `AdminActivityController`, read-only: no endpoint edits or deletes). `ActivityLog` throws `LogicException` on update/delete; mass query-builder deletes bypass that on purpose and only `activity:prune` uses one.
- Write ONLY through `App\Services\ActivityLogger::log(module, action, ?subject, changes, context, ?label, ?actor, ?actorLabel)`, explicitly and INSIDE the transaction of the action (rollback removes the row; a failed insert fails the action). No Eloquent observers: they lose the meaning of the action. Take the diff with `ActivityDiff::dirty($model)` between `fill()` and `save()` (or `ActivityDiff::between($before, $after)`); only changed fields are stored, as `{field: [before, after]}`. Log nothing when nothing changed.
- Redaction is central: `config('shop.activity.redact')` lists words; any field or context key whose NAME contains one (password, token, secret, api_key, signature, checksum, wompi…) becomes `[oculto]`. Personal data stays out: customer emails appear masked (`a***@dominio.com`) in `subject_label`, WhatsApp messages, phones and notes are never stored (notes only log that they changed). Failed logins keep the masked attempted email (100 chars max, `[valor no válido]` if it is not an email), never the password; a non-admin with the right password adds the note "sin permisos de administrador".
- New action or module: add it to `ActivityCatalog` (`MODULES`, `MODULE_ACTIONS`, `ACTIONS`, `FIELDS` for field names, `TYPES` + `labelFor` + `links` for a new subject). `orders.status_changed` is defined and tested but nothing calls it yet: the order management module must. Checkout orders and stock sales are NOT logged (customer actions; `inventory_movements` is their history); `inventory_movements` and the future order history stay as each domain's own history.
- Retention: `php artisan activity:prune` (scheduled daily 03:30 in `routes/console.php`) deletes only `module = 'auth'` rows older than `shop.activity.auth_retention_days` (`SHOP_ACTIVITY_AUTH_RETENTION_DAYS`, default 180). Administrative actions are kept. The listing hides "auth" unless "Incluir accesos" or the Accesos module is chosen. Exports (CSV `;`, BOM, formula guard) are logged as `activity/exported` and `customers/exported`.

## Users and roles

- Access is `users.role` (`App\Enums\Role`: admin, dispatch "Despacho y entrega", delivery "Solo entrega"), NOT `users.is_admin` (kept only as a dead legacy column; a later migration drops it; never read it). People are created in `/admin/users` (or `php artisan admin:create`, which asks for a username and makes an admin) and are never deleted, only deactivated (`is_active`). Sign-in is by `username` (lowercase, `[a-z0-9.-]`, 3-40, unique) or email.
- The permission matrix lives ONLY in `App\Support\Permissions` (`ALL` + one list per role). `AppServiceProvider` defines one Gate per permission from it; routes use `can:<permission>` (endpoints) or the `permission` key of the page in `routes/spa.json` (`RequirePagePermission`: the app shell with HTTP 403, React draws "No tienes acceso"). `/admin/session` returns `permissions`, `home` and `must_change_password`; the menu, pages and buttons are drawn from them, but the server is what enforces. A new page or endpoint = a permission in the matrix + its route guard; `UserRoleTest` fails if an admin route has none.
- Middleware order matters: `bootstrap/app.php` puts `EnsureStaff` and `Authorize` BEFORE route-model binding, so a missing session/permission answers 401/403 and never a 404 that reveals records. `EnsureStaff` also ends sessions whose `session_version` is not the user's (bumped by `UserService::closeSessions()` on deactivation, role change, password reset/change) and, while `must_change_password`, only lets `/admin/session`, `/admin/password`, `/admin/logout` and `/admin/change-password` through.
- Orders JSON is shaped ONLY by `OrderPresenter` from permissions: no email without `orders.view_customer_email`, no money/coupon/payments/payment status without `orders.view_financials`. A role with `orders.view_all` but without financials (dispatch) only gets active (`pending|confirmed|preparing|ready|shipped`) orders that pass `Order::valid()`, and the search never looks at emails (same query). Delivery (`orders.view_assigned`) lists in Pedidos only the orders assigned to them, delivered ones included as history; any other order id is 403. `orders.list` opens Pedidos for the three roles; `today.view` opens Hoy. Rows and cards carry `next` (the button of the next step for THAT person, from `OrderStatusService::nextAction`), so the frontend never decides it.
- `OrderStatusService` is the ONLY place `orders.status` changes: flow pending ("Pendiente de pago") -> confirmed ("Pagado") -> preparing -> ready ("Preparado") -> shipped ("En camino") -> delivered (422 otherwise). The labels live ONLY in `OrderStatusService::LABELS` and reach React through `/admin/session` (`order_statuses`, stored by `orderStatuses.js`; badges use the `order_<status>` key). pending -> confirmed happens ONLY in `PaymentService::markPaid` (the Wompi webhook, not integrated yet, and tests): no route, button or endpoint of the admin may confirm or mark as paid (`OrderFlowTest` guards it). While `shop.require_payment_before_fulfillment` is false pending -> preparing is also allowed ("Iniciar preparación"); when true only paid orders move. Steps (`PATCH /admin/orders/{id}/prepare|ready|ship|deliver`, ONE implementation used by Hoy and Pedidos, `resources/js/modules/admin/orderActions.jsx`) take `expected_status`: if somebody else moved the order first the answer is 409 "{name} ya movió este pedido a …" (`OrderMovedException`) and nothing is saved. Each step uses `lockForUpdate`, writes `orders.status_changed_at` (since when it is in the stage), an `order_status_history` row and an Historial row (`orders/status_changed`, with note, actor "Sistema" for a payment) in the same transaction, and dispatches `OrderStatusChanged` (and `OrderPaid`) AFTER the commit; no listeners yet (the emails will be). Ship needs exactly a delivery person (active, role delivery) or a carrier (+ optional tracking); delivering stores `delivery_note`; delivery-role people can only deliver orders assigned to them. Cancel/refund (`orders.cancel`, admin only) are defined but NOT implemented: the order management module will add them to this service. `reassign()` moves a shipped order to another courier.
- **Hoy** (`/admin/today`, `AdminTodayController`, `AdminToday.jsx`) is the home of the three roles: four sections (Nuevos = confirmed, plus pending while payment is not required; Preparando; Por enviar; Por entregar), oldest first, counters counted from the same list. Admin and dispatch get the four (dispatch without money/email); delivery only their own shipped orders. It refreshes every 30 s while the tab is visible. `/admin/deliveries` is a 301 to Hoy and the read-only Inventory screen no longer exists (`inventory.edit`, admin only, is the only inventory permission). `SCREENSHOT_HOY_ONLY=1 npm run screenshots` photographs Hoy for the three roles (needs a throwaway database with `alejandro` admin, `carlos.rojas` dispatch, `luis.mora` delivery, all with the password you pass in `SCREENSHOT_ROLE_PASSWORD`, and orders in every stage).
- `UserService` rules (422): nobody deactivates themselves, changes their own role or resets their own password from the panel; at least one active admin always remains; a courier with shipped, assigned orders cannot be deactivated or changed role until they are reassigned (the message lists the references). Every change is a Historial row of module `users` (never a password); temporary passwords are shown once in the response of create/reset. In the Historial, dispatch and delivery people appear as "Name · Role".
- Tests: `User::factory()` defaults to the `delivery` role; use `->admin()` or `->role('dispatch')`.

## Visual changes

**Every visual change to the storefront is verified with `npm run screenshots` before it is called done.** It needs the app running (`php artisan serve` + `npm run dev`, or a build) and writes 375 / 768 / 1440 px captures of `/`, `/promociones`, a product with a promotion, the open cart and the checkout summary to `storage/app/screenshots/` (git-ignored); open them and look at them. `SCREENSHOT_BASE_URL=http://127.0.0.1:8123 npm run screenshots` points it at another server (for example one with a throwaway SQLite database that has a promotion).

CSS gotcha: `demo-home.css` is one big scoped file with legacy rules. Before adding a class, `grep` for it; a duplicate name merges both rules (an old `.card-promo-badge` with top/right plus a new one with bottom/left stretched a badge over the whole image). New promotion badges use `.fh-discount-badge`.
